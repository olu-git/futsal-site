# Admin Fixtures data model (review only)

## Existing-schema findings

`public.fixtures` currently stores one row per match with draft/published visibility. A published row can be updated directly by an authenticated administrator under the existing grant and RLS policy. Such an edit would immediately change the public schedule. Making it a draft instead would hide it. Deleting/recreating it would change the ID and can break `result_versions.fixture_id`; it would also lose the original schedule outside the generic audit log. Existing `public.result_versions` protects published scores but does not prevent editing the fixture beneath them. The existing archived-season trigger already guards fixture rows. Team preference and note tables are admin-only. The public regular-season loader reads only published fixtures; current finals remain JSON-only.

The proposed migration revokes direct authenticated fixture writes and adds a proposal layer. The reviewed SQL RPC retains existing fixture IDs, leaves published fixtures untouched during draft/review, and changes them only in one PostgreSQL call. Privileged database owners/service-role operations remain outside this admin workflow and require separate operational controls.

## Tables and lifecycle

- `fixture_change_sets`: competition season, title, overall note, source (`manual`, `json_upload`, `system_import`), status, optimistic version, validation report, warning acknowledgement, creator/reviewer/publisher and timestamps.
- `fixture_change_items`: ordered update/create/cancel operation, original fixture and schedule version, item reason, proposed regular-season schedule and team IDs, optional display names.
- `fixture_change_history`: append-only reason and before/after row image for every published item. Existing `admin_audit_log` also records row mutations.
- `fixtures.schedule_status`: `scheduled` or `cancelled`. A cancellation keeps the fixture ID and row but sets `publication_state = 'draft'`, so existing public queries stop showing it. `fixtures.schedule_version` increments on structural schedule or visibility changes.

Only `draft -> pending_review -> published` can publish. A pending plan can return to draft; a draft or pending plan can be cancelled. Published/cancelled plans and their audit history are immutable. A later correction is a new change set using the then-current fixture version. Returning to draft clears warning acknowledgement. A plan with blocking messages cannot enter review or publish; warnings require explicit acknowledgement and are retained in `validation_report`.

## Validation and publication

The versioned JSON parser is strict and identifies a single competition season. `src/lib/admin/fixture-changes.ts` builds a projected schedule and returns ordered blocking errors, warnings and informational messages. It checks team/fixture identity, stages, versions, date/time/court, collisions, completed fixtures, time preferences, team notes/status, short turnarounds and uneven rounds. Display names are advisory; UUIDs are authoritative. `fixture-change-service.ts` defines the future browser repository contract and produces before/after comparisons without writing data.

Court occupancy is keyed by **physical location + date + kick-off time + court**, not by division or competition season. Location is resolved through fixture -> competition season -> competition -> location; no location is copied onto a change item. Published, scheduled fixtures in non-archived active or published editions at that location occupy a slot, including other competitions and divisions. Draft/cancelled fixtures do not. The local validation context must load all such venue fixtures and the relevant competition/edition relationships, not only the selected edition; `loadValidationContext` is the future repository boundary for that read. Another venue may use the same court number and time.

Both validators evaluate the **final** schedule: they exclude the original slots of every targeted fixture, apply cancellations, then compare all proposed updates/creates against unchanged occupied slots and against each other. Thus a cancellation/replacement or two-fixture court swap can publish together, while an unchanged fixture in another division still blocks a collision. The current per-edition unique index remains a second line of defence, but cannot by itself enforce venue-wide occupancy.

The SQL RPCs are `create_fixture_change_set`, `replace_fixture_change_items`, `validate_fixture_change_set`, `transition_fixture_change_set` and `publish_fixture_change_set`. All verify `private.is_admin()`. Direct DML grants on new tables and `public.fixtures` are removed from `authenticated`; the RPCs are the only intended admin write path. New tables have RLS and admin-only read policies. Anonymous visitors and non-admin authenticated users cannot read plans. No fixture change can target an archived competition season.

`publish_fixture_change_set` first locks the physical `locations` row, then the competition edition, plan and affected fixtures. Every Admin Fixtures publication at the same venue therefore waits on the same row, even when the plans target different divisions. After acquiring the venue lock, the RPC rechecks location-wide occupancy, completed-result protection, optimistic versions and previously acknowledged warnings under PostgreSQL's normal `READ COMMITTED` transaction isolation. The second publisher sees the first publisher's committed fixtures and is rejected if it now collides; reviewers must return its changed plan to draft. It temporarily unpublishes affected rows inside the transaction so slot swaps do not trip the existing unique index, applies every item, writes before/after history, and marks the plan published last. Other transactions continue to see the old public schedule until commit. Any error rolls back the entire call. Completed fixtures are blocked rather than offering an exceptional correction path in this release. New fixtures receive a generated UUID as both their ID and legacy public identifier, allowing the existing snapshot generator to include them. Privileged direct writes outside these RPCs must follow separate scheduling controls; this migration revokes direct fixture writes from browser-authenticated administrators.

Current grading and knockout JSON, public pages and Admin Results are not changed by this release. The current 2026 regular season is complete; this model is intended for future regular-season scheduling. It preserves Codex-assisted scheduling: Codex can propose the strict JSON file, an administrator can review the before/after plan and warnings, and only an explicit reviewed RPC publication can make it public.

## Manual migration and rollback

1. Review `supabase/migrations/202609270001_fixture_change_sets.sql` and back up the target project. Apply it first to a disposable/local Supabase database with the two prior migrations and a confirmed FIS admin already present.
2. Run `supabase/verification/verify_fixture_change_sets.sql` in that disposable database. It starts a transaction, exercises security, venue conflicts, an atomic court swap, cancellation and publication, and ends with `ROLLBACK`; it must finish without an assertion error. For a live concurrency check, use two disposable admin sessions with separate reviewed plans targeting the same free venue slot: publish both concurrently and verify that exactly one succeeds. The single-session script checks that the location-row lock is present but cannot reproduce two simultaneous transactions.
3. Inspect grants, RLS, archived-season behavior, published fixtures and results in the disposable database. Review direct admin writes by any older tools, because this migration intentionally revokes them.
4. Only after separate approval, apply the migration through the controlled Supabase migration process. Refresh PostgREST's schema cache if the new RPCs are not immediately visible. Do not import the current knockout JSON.
5. For an activation problem, stop use of the new RPCs and keep existing published fixtures visible. Restore from a tested database backup or create a forward corrective migration; do not casually drop the new columns/tables or delete history. No SQL was applied as part of this implementation.

The verification script uses far-future disposable fixture rows and never modifies Auth users or `private.admin_users`. Its test trigger is created inside the rollback transaction solely to prove all-or-nothing publication.
